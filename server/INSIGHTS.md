## What Works

- **2026-09-18** — `pnpm arch:check` (dependency-cruiser, `server/.dependency-cruiser.cjs`) enforces the onion ring rules and is the fastest way to tell whether a backend change broke layering. Baseline on this branch is 20 violations / 0 errors, ALL pre-existing warnings — so the check is only meaningful as a DELTA, not as a pass/fail count, and it exits 0 on warnings. It caught a real regression during this session: adding a workspace guard inline in `modules/repo-intel/routes.ts` tripped `routes-not-to-orm` (a route building its own SQL skips rings 3 and 2 and re-implements scoping per endpoint). The rule's own comment states the fix — move the query into the module's repository and call it from the service — which dropped the count back to the 20 baseline. Evidence: `server/.dependency-cruiser.cjs:80`, `server/src/modules/repo-intel/service.ts:107`.
- **2026-09-18** — fflate's `unzipSync` runs its `filter` callback BEFORE inflating each entry, which is what makes "we never open the executable parts of an imported archive" a real guarantee rather than a promise. The skill importer uses two passes (`modules/skills/import-parse.ts:185`): pass 1 filters everything OUT purely to collect entry names + `originalSize` from the central directory, pass 2 accepts exactly the one markdown entry. A single-pass `unzipSync(bytes)` would decompress install.sh and tool.exe into memory before you could choose. The property is testable without touching the filesystem: wrap the module with `vi.mock('fflate')` and record which names each call's filter returned true for — `test/skills-import.test.ts` asserts `[[], ['my-skill/SKILL.md']]`. `vi.spyOn(require('fflate'), 'unzipSync')` does NOT work: the importer holds a named ESM binding, so the spy never fires and the assertion silently sees zero calls.

## What Doesn't Work

- **2026-09-15** — A clean checkout cannot boot the API with `scripts/dev.sh` alone: it installs deps only in `server/` and `client/`, never in `reviewer-core/`. The server imports reviewer-core SOURCE through a tsconfig alias (`server/tsconfig.json:24`), so Node resolves that file's bare imports upward from `reviewer-core/src/llm/` and NEVER reaches `server/node_modules` — they are sibling dirs, not nested. Boot dies on `ERR_MODULE_NOT_FOUND: Cannot find package 'openai' imported from reviewer-core/src/llm/structured.ts`. Fix: run `npm ci` in `reviewer-core/` (npm, not pnpm — it carries a `package-lock.json`).
- **2026-09-15** — A single failed background job KILLS the whole API process. `JobRunner.enqueue` marks the row `status:'failed'` and then RETHROWS (`server/src/platform/jobs.ts`, catch block), which rejects the returned `done` promise — but every call site awaits only `enqueue(...)` itself (which resolves immediately with `{id, done}`) and never attaches a handler to `done`. Under Node 22's default `--unhandled-rejections=throw` the process exits. Concrete trigger: the seeded demo repo `acme/payments-api` does NOT exist on GitHub, so any clone / refresh / reindex on it fails with `GitError: Repository not found` and takes :3001 down. The symptom is deeply misleading — Next.js on :3000 still serves 200, so the UI renders with empty lists and looks like the DATABASE was wiped, while every row is actually intact. Diagnose with `curl localhost:3001/health` before suspecting data loss. Evidence: `server/src/platform/jobs.ts`, `server/src/modules/repos/service.ts:98,117`.
- **2026-09-16** — `pnpm exec vitest run --exclude '**/*.it.test.ts'` is NOT green on a clean Windows checkout: 6 tests in `server/test/indexer-pipeline.test.ts` fail with `ENOENT … \src\a.ts` from the test's own `writeFileAt` helper (it splits paths on '/' only, so nested fixture dirs are never created). Verified by stashing all local work and re-running on plain `origin/main` — do NOT attribute these 6 to your change; the rest of the suite (95 tests) passes. Evidence: `server/test/indexer-pipeline.test.ts:142-144`.
- **2026-09-16** — Firing several LARGE reviews at once hangs them. Four concurrent runs on a 5,290-line diff (three agents via "Review all" plus one more) left two stuck after the `Reviewing N changed file(s) in one pass` event with no further activity for 30+ minutes, while serial runs on the SAME diff finished in 1-3.5 min. That is far past the configured ceiling: the provider is built with the defaults (90s per request, <=2 SDK retries) and the engine adds <=3 schema-repair attempts, which bound a run near 13 min. Recovery is `POST /runs/:id/cancel` — a cancelled run stores `cost_usd: null`, so it does not pollute PR-list totals. Until the cause is known, run large-diff reviews one at a time. Evidence: `server/src/platform/container.ts:185`, `reviewer-core/src/llm/openrouter.ts:54`.
- **2026-09-18** — A blanket architecture rule 'pure/rule files must not import the db layer' CANNOT be written against `src/db/` — it flags every legitimate DTO mapper. `modules/*/helpers.ts` reach for row types via `import * as t from '../../db/schema.js'` and then `typeof t.repos.$inferSelect` (`repos/helpers.ts:2,44`), which is a VALUE import syntactically even though only types are used, so dependency-cruiser sees a real edge. Translating a row to a snake_case DTO is exactly what a mapper is for, so this is not a violation. The rule that actually works targets the connection and the wiring instead — `^src/db/client\.ts$`, `^src/platform/(container|jobs|sse)\.ts$`, `^src/adapters/` — and is clean today at severity `error`. Evidence: `server/.dependency-cruiser.cjs:48`, `server/src/modules/repos/helpers.ts:44`.
- **2026-09-18** — Per-skill STATISTICS cannot be derived from the tables that exist today — nothing anywhere attributes a run or a finding to a skill. `findings` has only `review_id` (`db/schema/reviews.ts:35`), `agent_runs` has only `agent_id`/`pr_id` (`db/schema/runs.ts:8`), and the single record of which skills a run actually carried is the opaque `prompt_assembly.skills` STRING inside the `run_traces` jsonb document (`modules/reviews/run-executor.ts:283`). `agent_skills` answers only what is linked RIGHT NOW, not what any past run used, so a stats page built on it silently re-labels history every time someone edits the picker. A grep of `db/schema/` for skill finds exactly three tables — `skills`, `skill_versions`, `agent_skills` — so unlike the rest of L02 this one genuinely needs a new table (a `run_skills` join carrying run_id, skill_id, skill_version), generated with `pnpm db:generate`. The jsonb fallback (scan every trace document) parses but is a document scan per request, not an index. Second, non-obvious consequence: even with that table the attribution is CO-OCCURRENCE, not causation — every skill in the prompt gets credited with every finding of that run — so an accept-rate or pull-frequency number presented per skill is precision the data cannot support.

## Codebase Patterns

- **2026-06-14** — Shared contracts (`@devdigest/shared`) are vendored as TWO hand-maintained copies — `server/src/vendor/shared/` and `client/src/vendor/shared/` — resolved by tsconfig path alias, NOT auto-synced. Adding a field means editing both in lock-step; the only diffs between copies are comments. Evidence: `server/src/vendor/shared/contracts/trace.ts:61`, `platform.ts:157`.
- **2026-06-14** — PR-list per-PR aggregates (score, cost) are computed ON READ in `GET /repos/:id/pulls` via one `inArray` query + JS grouping, never denormalized onto `pull_requests`. "Latest review batch" cost has no batch id in the schema — approximated by summing `agent_runs.cost_usd` within a 120s window of the PR's newest priced run. Evidence: `server/src/modules/pulls/routes.ts:138`. (SUPERSEDED 2026-09-16 — see the entry below: the column is now the sum of ALL successful runs.)
- **2026-06-14** — `completeAgentRun`'s `values` shape is declared in TWO places that must match: the repo fn (`repository/run.repo.ts`) AND the interface wrapper (`repository.ts:151`). Adding a field (e.g. `costUsd`) needs both or typecheck fails.
- **2026-09-16** — The PR-list batch-cost RULE now lives in `server/src/modules/pulls/cost.ts` (`costByPrFromRuns`), not inline in `pulls/routes.ts` — the route only runs the query and hands the newest-first rows to it. Same split as `pulls/status.ts`/`deriveReviewStatus`, and the reason is testability: the rule gets unit coverage in `server/test/pulls-cost.test.ts` with no database, while a route-inline loop would need an `.it.test.ts`. Put new PR-list rollups there too. Evidence: `server/src/modules/pulls/cost.ts:33`, `server/src/modules/pulls/routes.ts:133`.
- **2026-09-16** — The PR-list COST column is a RUNNING TOTAL: the sum of every `status='done'` run's `cost_usd` for that PR, so re-reviewing adds to it. This supersedes the earlier 120s-"latest batch" window (dropped 2026-09-16) — the course acceptance criterion defines the column as "сума вартості всіх успішних прогонів". The per-run breakdown stays on the PR page; failed/cancelled runs and un-priced runs contribute nothing, and a PR with no priced run serializes `null` ("—"), never 0. Evidence: `server/src/modules/pulls/cost.ts:26`, `server/test/pulls-cost.test.ts:21`.
- **2026-09-16** — The PR-list FINDINGS breakdown (`server/src/modules/pulls/findings.ts`, `findingsByPrFromRows`) is deliberately scoped to the SAME latest review the `score` column reads (`kind='review'`, newest `created_at`), so one row can never show a score and a breakdown from different runs. It is NOT a running total — unlike COST, re-reviewing REPLACES it. Two states that must stay distinguishable on the wire: a PR with no review is absent from the map → `null` ("—"), while a reviewed-but-clean PR is `{0,0,0}`. Caveat inherited from `score`: with a "Review all" fan-out each agent writes its own review row, so "latest" means ONE agent's review, not the whole batch — `reviews.runId` is the field to group on if that ever needs changing. This finally uses `rollupSeverities()`, which had been written and left uncalled. Evidence: `server/src/modules/pulls/findings.ts:33`, `server/src/modules/pulls/routes.ts:120`, `server/src/modules/pulls/status.ts:23`.
- **2026-09-16** — The `findings` table has NO `workspace_id` (nor `pr_id`/`run_id`) — its only FK is `review_id`. Tenancy is inherited TRANSITIVELY through `reviews.workspaceId`, so a findings query is only safe when its `review_id IN (…)` list came from an already workspace-scoped read. You cannot query findings by PR directly, and you must never add a findings query scoped by `pr_id` alone. Evidence: `server/src/db/schema/reviews.ts:28`, `server/src/modules/pulls/routes.ts:133`.
- **2026-09-16** — Two endpoints disagree about what a "review" is, and a client that takes `reviews[0]` will silently show the wrong run: `GET /pulls/:id/reviews` returns BOTH kinds newest-first (`reviewsForPull` does not filter `kind`), while `GET /repos/:id/pulls` computes `score`/`findings` from `kind='review'` only. Any consumer pairing the two must filter `kind === "review"` itself. Evidence: `server/src/modules/reviews/repository/review.repo.ts:57`, `server/src/modules/pulls/routes.ts:124`.
- **2026-09-18** — 4 of the 5 import cycles in `server/src` are the SAME defect wearing different paths: `service -> platform/container.ts -> service`. The container imports a service to construct it (`_repoIntel ??= new RepoIntelService(this)`, `container.ts:118`) while the service imports the container to reach its dependencies (`constructor(private container: Container)` in repos/reviews/agents/repo-intel `service.ts`). Fixing the constructors to take the ports they actually use (GitClient, SecretsProvider, the repository) instead of the whole Container removes all four cycles at once — they are a symptom, not four separate problems. The 5th is unrelated: `agents/helpers.ts <-> agents/repository.ts` over row types, fixable by moving them to the existing `db/rows.ts`. Invisible until something measured it: run `cd server && pnpm arch:check`. Evidence: `server/src/modules/repos/service.ts:36`, `server/src/platform/container.ts:118`.
- **2026-09-18** — The vendor/shared lock-step is no longer discipline-only — `server/test/vendor-shared-sync.test.ts` (and its twin `client/src/test/vendor-shared-sync.test.ts`) now assert the two copies have the SAME file list AND are BYTE-identical. This tightens the earlier 2026-06-14 note that 'the only diffs between copies are comments': comments must match too, and the server copy is canonical because reviewer-core compiles against it. The test is duplicated into both packages on purpose — CI filters jobs by path (`.github/workflows/{client,server-unit}.yml`), so a client-only change must fail the client job and a server-only change the server job; a single copy would let half the drift through. Its header records why it exists: 5 of 11 files had already drifted, three of them Zod schemas whose enums no longer admitted 'openrouter'. Don't hand-roll a lock-step check — run this one. Evidence: `server/test/vendor-shared-sync.test.ts:43`, `client/src/test/vendor-shared-sync.test.ts:1`.
- **2026-09-18** — L02 needed NO migration and NO new contract: `skills`, `skill_versions` and `agent_skills(order)` were already created by `0000_init.sql`, `Skill`/`SkillType`/`SkillSource`/`AgentSkillLink` already lived in `vendor/shared/contracts/knowledge.ts:114-199`, the agent side of the link (`GET`/`POST /agents/:id/skills`, `setSkills` in one transaction) was already implemented in `modules/agents/`, and `reviewer-core`'s `skills` prompt slot + `## Skills / rules` section already existed and were simply unfed (`reviewer-core/src/prompt.ts:88,109,131`). The whole feature was a `modules/skills/` CRUD module, one line in `modules/index.ts`, and ~8 lines in `run-executor.ts`. Before building any later-lesson feature, grep `db/schema/`, `vendor/shared/contracts/` and `reviewer-core/src/prompt.ts` for it first — `seed.ts`'s header comment names the tables that are waiting ("skills, conventions, memory, eval, …").
- **2026-09-18** — A NEW module must not copy the `constructor(private container: Container)` shape the four existing services use. Writing `SkillsService(container)` took `pnpm arch:check` from its 20-warning baseline to 21 by tripping `service-not-to-composition-root`; the rule's own comment says to inject the ports the service actually uses. The fix was `constructor(private repo: SkillsRepository)` with `routes.ts` doing `new SkillsService(new SkillsRepository(app.container.db))` — service.ts then no longer imports `platform/container.js` at all, the count went back to 20, and the workspace-scoping integration test could drive the service with a plain repository instead of casting a fake Container. The composition happening in `routes.ts` is not itself a violation: `routes-not-to-orm` matches only direct edges to `db/schema` / `db/client.ts`.
- **2026-09-18** — `skills` is the ONE prompt slot `assemblePrompt` does not `wrapUntrusted`, and that omission becomes a live prompt-injection hole the moment a lesson lets users IMPORT a skill. reviewer-core's type comment says it out loud — 'trusted-ish; community skills should be sanitized upstream' (`reviewer-core/src/prompt.ts:42`) — and `modules/reviews` is that upstream. The fix keeps reviewer-core pure: `renderSkillBlock` (`modules/reviews/helpers.ts`) wraps the body of an `imported_url`/`community` skill with the engine's own exported `wrapUntrusted('skill:<name>', body)`, which is what brings it under the INJECTION_GUARD already appended to every system prompt. A `manual`/`extracted` body must NOT be wrapped — those are the user's own rules, and demoting them to data makes the feature inert. Name and description stay outside the wrapper so the trace block is still readable. `wrapUntrusted` also escapes a body that tries to close the delimiter itself, so a hostile `</untrusted>` cannot break out. Marking imported skills `enabled:false` is a human control, not a substitute for this.
- **2026-09-18** — A skills VERSION-HISTORY API is a transplant, not a design: `SkillsRepository.listVersions` (`modules/skills/repository.ts:155`) is fully written — newest-first `desc(version)` over `skill_versions` — and has NO caller anywhere in `src` or `test`, while `modules/agents` already ships the same feature across all three layers (`repository.ts:172` -> `service.ts:116` -> `routes.ts:129`). Copy the agents shape rather than inventing one, and copy its tenancy guard in particular: the service resolves the OWNER row by workspace first and returns `undefined` when it does not match, because `skill_versions` (like `agent_versions` and `findings`) has no `workspace_id` of its own and inherits tenancy transitively — a route that passes an id straight to `listVersions` leaks another workspace bodies. `server/test/agents-versions.it.test.ts:174` is the ready-made assertion pair for that (`toHaveLength(1)` in the owning workspace, `toBeUndefined()` in the other).

## Tool & Library Notes

- **2026-06-14** — New DB columns: edit `db/schema/*.ts`, then `npm run db:generate` (drizzle-kit) auto-generates `00NN_*.sql` (e.g. `0010_solid_baron_zemo.sql` = `ALTER TABLE … ADD COLUMN`). Never hand-write migration SQL; apply with `npm run db:migrate`. Evidence: `server/package.json:12`.
- **2026-09-16** — `reviews.createdAt` is `defaultNow()`, so an `.it.test.ts` that needs a deterministic "latest review" MUST pass `createdAt` explicitly when inserting — two rows inserted back-to-back can otherwise share a timestamp and the newest-first ordering becomes arbitrary. Same discipline the cost integration test already applies to `agentRuns.ranAt`. Evidence: `server/src/db/schema/reviews.ts:25`, `server/test/integration.it.test.ts:213`.
- **2026-09-18** — dependency-cruiser rules that target an npm package must match its RESOLVED path, not the bare package name — and under pnpm that path is `node_modules/.pnpm/<pkg>@<ver>_<peers>/node_modules/<pkg>/index.d.ts`. A rule written as `to: { dependencyTypes: ['npm'], path: '^drizzle-orm' }` silently matches NOTHING (no error, no warning — it just never fires); `path: 'node_modules/drizzle-orm'` as an unanchored substring works and survives version bumps. Same trap for any future package rule. Also needed for this repo: `tsConfig: { fileName: 'tsconfig.json' }` so the `@devdigest/shared` and `@devdigest/reviewer-core` path aliases resolve, and `tsPreCompilationDeps: true` so type-only imports still count as edges (with the default `false`, TS elides them and boundary violations expressed purely in types disappear from the graph). Evidence: `server/.dependency-cruiser.cjs:104`.
- **2026-09-18** — The two vendored `@devdigest/shared` copies are now guarded by a test in BOTH packages (`server/test/vendor-shared-sync.test.ts`, `client/src/test/vendor-shared-sync.test.ts`) — the hand-sync rule finally has teeth, after 5 of 11 files had silently drifted (three of them Zod enums missing `openrouter`). Two things the guard had to learn: compare with line endings NORMALISED, because a `git stash`/`pop` on Windows rewrote one copy to CRLF and the other stayed LF — that is a checkout artefact, not drift, and byte equality flags it; and anchor paths on `process.cwd()`, not `import.meta.url`, because the client half runs under jsdom where `import.meta.url` is not a file URL and `fileURLToPath` throws at collection time. Evidence: `server/test/vendor-shared-sync.test.ts:26`, `client/src/test/vendor-shared-sync.test.ts:21`.
- **2026-09-18** — The 6 known-failing `server/test/indexer-pipeline.test.ts` tests are FIXED — verified directly today with `pnpm exec vitest run test/indexer-pipeline.test.ts` (11/11 pass) and a full `--exclude '**/*.it.test.ts'` run (118 tests / 20 files, all green, up from the 95 recorded on 2026-09-16). Two places still assert they fail and will now mislabel a REAL regression as pre-existing: the 2026-09-16 'What Doesn't Work' entry above, and `.claude/skills/pr-self-review/baseline.json`, whose `known_failing_tests[0]` the pr-self-review gate reads to print 'known-failing (Windows, unrelated)'. That file's own `_comment` says to remove an entry the moment the bug is fixed — a hardcoded failure baseline rots silently and then suppresses signal, which is worse than having none. Drop the entry when next touching that skill. Evidence: `.claude/skills/pr-self-review/baseline.json:7`, `server/test/indexer-pipeline.test.ts`.
- **2026-09-18** — Appending a large TypeScript template-literal constant (a 5KB agent prompt mirrored from `docs/agent-prompts/*.md`) cannot be done through the Bash heredoc on this Windows setup — a quoted `<<'JS'` heredoc still lost one level of backslash, so `.replace(/\\/g, ...)` arrived as `.replace(/\/g, ...)` and died with "Invalid regular expression: missing /". Two things that DO work: write the helper script with the `Write` tool instead of a heredoc, or keep the script backslash-free by building the escapes from `chr(92)`/`chr(96)` in a Python heredoc. Whichever route, escape in this order — backslash, then backtick, then `${` — and verify with `pnpm typecheck` rather than eyeballing, since an unescaped backtick only fails at compile time. Same trap applies to any generated `seed-prompts.ts` entry.
- **2026-09-18** — `pr-self-review`'s `gate.mjs` matches a findings file to a route by SLICE FILENAME, so a sliced reviewer must write `findings/<skill>-<slice>.json` — and a STALE `findings/<skill>.json` left over from an earlier run silently wins for slice 1. On this branch that dropped two real frontend findings into the '## Dropped findings' table as 'cites a file not assigned to this reviewer', which reads like a reviewer error rather than a cache problem. Always `rm -f .devdigest/cache/pr-self-review/findings/*.json` before a re-run. Second trap in the same script: `verdict.json`'s `dirty_hash` is computed when the GATE runs, not when the reviewers ran, so fixing findings and then running only phase 5 stamps a stale verdict with a fresh hash — exactly defeating the staleness check the SKILL.md prescribes. Re-run phases 1-3 after any fix.
- **2026-09-18** — CORRECTION to the earlier entry about `pr-self-review`'s findings files: `gate.mjs` does NOT match them per slice. It reads findings from EVERY `*.json` in `findings/`, but its completeness check (`gate.mjs:98-101`) requires exactly `findings/<skill>.json` for each ROUTED SKILL — so a sliced skill still needs ONE file under its bare name, while `reviewer-prompt.md` tells you to write `<skill>-<slice>.json`. Following the template verbatim yields `INCOMPLETE: no findings file — reviewer did not report` even though both slice reviewers replied. Write the per-slice replies into one merged `<skill>.json` (or the template's files PLUS a bare one, at the cost of double-counted findings). The first run on this branch only appeared to work because a STALE `frontend-ui-architecture.json` from an earlier session satisfied the check — and its old findings were merged in while the fresh slice files' findings were dropped as 'cites a file not assigned to this reviewer'. Still true: `rm -f findings/*.json` before every re-run.

Verified the guard by temporarily restoring the long literal and watching it fail with `too_big/maximum: 200`. Any future table seeded past its own write schema deserves the same one-line test.
