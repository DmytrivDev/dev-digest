## What Works

- **2026-06-14** — `formatCost` (`client/src/lib/cost.ts:13`) distinguishes MISSING data (`null`/`undefined` → "—") from a genuine zero (`0` → "$0.00"), widens precision for sub-cent values (~2 sig figs), and trims trailing zeros to a 2dp floor ("$0.06" not "$0.060", "$0.0013" not "$0.00"). Reuse it for any per-run money display.
- **2026-09-16** — The reference mock `DevDigest Design (standalone).html` is a self-extracting bundle (gzip+base64 chunks in `<script type="__bundler/manifest">`, each chunk a readable `.jsx` named in its first-line comment) — but before porting anything from it, check `client/src/vendor/ui`: the design system is ALREADY vendored there. `SEV` (severity colour/icon/label tokens), `Chip` (icon + label + count + active), `SeverityBadge` (compact/count), `CategoryTag`, `ConfidenceNum`, the `ddpop` keyframe and `--shadow-modal`/`--border-strong` all exist. Porting a mock screen is composition of existing primitives, not new CSS. Evidence: `client/src/vendor/ui/primitives/tokens.ts:6`, `primitives/Chip.tsx:4`, `vendor/ui/styles.css:255`.
- **2026-09-16** — Hover-lazy data without touching the hook: `usePrReviews(prId)` hardcodes `enabled: !!prId` and takes no options object, so a per-row hover fetch looks like it needs the signature widened. It does not — render the consuming component only while hovering (`{hover && <FindingsTooltip prId={...} />}`) and the hook mounts (and fires) lazily, with TanStack caching the result per PR. Same trick applies to any of the single-arg hooks in `lib/hooks/`. Evidence: `client/src/lib/hooks/reviews.ts:51`, `client/src/app/repos/[repoId]/pulls/_components/FindingsCell/FindingsCell.tsx:44`.
- **2026-09-16** — To visually verify a UI state the dev DB cannot currently produce, stub `window.fetch` in the browser tab instead of mutating the dev DB (the seeded PR #482 accumulates empty mock reviews, and since the list reads only the LATEST review, its FINDINGS cell legitimately renders "—" even though findings exist on older runs). Wrap the real fetch, rewrite only the matching JSON responses, then `window.dispatchEvent(new Event("focus"))` — `usePulls` has `refetchOnWindowFocus: true`, so the stub takes effect without a reload that would discard it. Reverting = restore the saved original and navigate. This renders the REAL component tree, so it catches layout/clipping bugs RTL cannot, and leaves the user's data untouched. Evidence: `client/src/lib/hooks/core.ts:110`, `docs/visual-test-findings-severity.md:0`.
- **2026-09-18** — The reference mock answers "what was this screen supposed to be" WITHOUT decompressing it: the artboard registry is plain text in the raw HTML, so `grep -o "Skill Editor[^\"<]*" "DevDigest Design (standalone) (3).html"` lists every variant of a screen (Config / Preview / Evals / Stats / Versions) and `grep -o ".\{300\}<label>.\{300\}"` shows which `window.Screen*` component and `tab=` prop renders it. Only then is extraction worth it: the gzip+base64 chunks under `<script type="__bundler/manifest">` decompress to named `.jsx` files (`screen_skills.jsx`, `screen_agents.jsx`, `primitives.jsx`, `charts.jsx`) whose first-line comment is the name. Two concrete payoffs this session: the mock ALREADY drew the agent Skills tab with a drag handle (`Icon.Menu`, `cursor: "grab"`) and the hint "Drag to reorder", so the arrows shipped in L02 were a deliberate downgrade and not the design; and `SkillStatsTab`/`SkillVersionsTab` exist in full, composed entirely from primitives this repo already vendors (`Donut`, `CircularScore`, `Card`, `SectionLabel`, `MonoLink`, `Badge`, `EmptyState`). Write the extractor with the `Write` tool, not a Bash heredoc — a heredoc eats one level of backslash and the path-sanitising regex dies with "Invalid regular expression: missing /".
- **2026-09-19** — A form over data that arrives ASYNC does not need an effect or a `key` remount: hold each field as a nullable OVERRIDE and derive what is shown — `const shown = name ?? draft.data?.name ?? ""`. Null means untouched, so the fields fill themselves when the query resolves after the first render, and the submit can send only the fields that differ from the draft. That second half is not cosmetic here: `POST /repos/:id/conventions/skill` reads an omitted field as "use what the server assembled", and the byte-identical save is what keeps an unchanged accepted set from burning a skill version. Contrast `SkillEditor`, which mirrors props into state and remounts with `key={skill.id}`. Evidence: `client/src/app/repos/[repoId]/conventions/_components/ConventionsView/_components/SkillDraftModal/SkillDraftModal.tsx:47`.

## What Doesn't Work

- **2026-09-16** — On Windows a long-running `pnpm dev` (Next 15) can serve a STALE compiled chunk indefinitely: after editing `RunCostBadge.tsx` the browser kept rendering the pre-edit output while `.next/static/chunks/app/repos/[repoId]/pulls/[number]/page.js` still contained the old `toLocaleString()` call. A hard navigation AND `touch`ing the source both failed to trigger a recompile — only killing the dev server and restarting `pnpm dev` picked the change up. When a UI change 'has no effect' but `pnpm typecheck`/`pnpm test` agree with your source, grep `.next/` for the compiled string before debugging the component. Evidence: `client/package.json:6`, `client/src/components/RunCostBadge/RunCostBadge.tsx:41`.
- **2026-09-16** — A floating panel anchored inside a PR-list row is clipped TWICE over, both silently. (1) `s.tableCard` shipped `overflow: "hidden"`, so an `position:absolute` popup in a row was cut off at the card edge — it must be `"visible"` (the reference mock sets it for exactly this reason). (2) `PRRow.test.tsx` asserts `row.children.length === COLUMN_KEYS.length`, so the panel must be nested INSIDE its cell; rendering it as a row-level sibling fails that guard. Note the app scroll container is `<main>` with `overflow: auto`, which is why the popup flips placement up/down by row index rather than relying on the viewport. Evidence: `client/src/app/repos/[repoId]/pulls/styles.ts:98`, `_components/PRRow/PRRow.test.tsx:73`, `_components/FindingsCell/FindingsCell.tsx:44`.
- **2026-09-18** — The in-app browser pane can serve a STALE frame for minutes when Claude's window is behind another window: `computer screenshot` returned a skills page stuck on loading skeletons and a "No repo selected" repo switcher, while `performance.getEntriesByType('resource')` showed `/skills` and `/repos` had both returned in ~10ms and `document.querySelector('main').innerText` contained every card. One screenshot call even failed outright with "the page did not finish rendering in time … Claude's window may be behind another window". Do not debug a React Query "hang" from a screenshot — confirm with `javascript_tool` against the DOM or `get_page_text` first. Useful corollary: driving the UI entirely through `javascript_tool` (read the DOM, `.click()` a button, re-read) verifies behaviour reliably while the pane is not drawing, and lets you count writes by temporarily wrapping `window.fetch`.
- **2026-09-18** — The FIRST value import from `@devdigest/shared` on the client breaks the Next build, and neither `pnpm typecheck` nor `pnpm test` notices. Every client import of that package had been `import type` / `export type` (checked: `lib/types.ts`, `lib/hooks/reviews.ts`), and TypeScript erases those — so nothing had ever asked webpack to resolve the vendored barrel at runtime. Adding `import { SKILL_LIMITS } from "@devdigest/shared"` to a component made it resolve `src/vendor/shared/index.ts`, whose ESM-style `export * from "./contracts/findings.js"` specifiers have no `.js` file behind them, and the dev server died with `Module not found: Cannot resolve ./contracts/findings.js`. `tsc` maps the extension itself and vitest runs through Vite, which already applies the alias, so both stayed green on a page that would not render. Fix: `webpack: (config) => { config.resolve.extensionAlias = { ".js": [".ts", ".tsx", ".js"], ".mjs": [".mts", ".mjs"] }; return config; }` in `client/next.config.mjs`, keeping `.js` last so real JavaScript still resolves. Verified with `pnpm build`, not with the dev server. The general rule: a change that turns a type-only dependency into a runtime one must be checked with a BUILD, because the unit suites cannot see it.
- **2026-09-19** — The global `MutationCache.onError` toasts EVERY mutation failure, so a route whose 4xx is an ANSWER gets a system error toast on top of whatever the page renders inline: the conventions scan replies 422 for "no clone"/"no index" and 429 for its 5-per-minute rate limit, and both looked like a broken app next to their own explanation. There is no per-`useMutation` opt-out in TanStack v5 — the cache handler always runs — but its 4th argument IS the mutation, so the opt-out has to be a flag it reads: `onError: (err, _v, _c, mutation) => { if (mutation.meta?.quietError) return; ... }`, with `meta: { quietError: true }` on the mutation. Queries already had this distinction (they toast only on status 0 / 5xx); mutations did not. Evidence: `client/src/lib/providers.tsx:33`, `client/src/lib/hooks/conventions.ts:44`.
- **2026-09-19** — A dark theme built purely from CSS variables does NOT darken the widgets the BROWSER paints: the native `<select>` popup opened white-on-white over the dark app (the Conventions category picker), and so do scrollbars and date pickers. Styling the `<select>` is not enough — the popup inherits the control's own background, and `background: "transparent"` (what `kit/SelectInput.tsx` shipped) resolves to the UA default rather than to the parent. The fix is one declaration per theme block in `vendor/ui/styles.css`: `color-scheme: dark` under `:root, [data-theme="dark"]` and `color-scheme: light` under `[data-theme="light"]`, which is what tells the engine to render its own chrome dark; Chromium additionally honours `backgroundColor`/`color` set on the `<option>` rows, so both are set. Verify from the DOM, not a screenshot — the popup is an OS window and never appears in a captured frame: `getComputedStyle(document.documentElement).colorScheme` and the select's computed `backgroundColor` are the evidence. Evidence: `client/src/vendor/ui/styles.css:9`, `client/src/vendor/ui/kit/SelectInput.tsx:31`.

## Codebase Patterns

- **2026-06-14** — Cross-route shared components live in `src/components/<Name>/` with an `index.ts` barrel, imported via `@/components/<Name>` (e.g. `RunCostBadge`, `diff-viewer`). Vendored UI primitives (`Badge`, `CircularScore`) live in `src/vendor/ui` under `@devdigest/ui` — different home. Evidence: `client/src/components/RunCostBadge/index.ts:3`.
- **2026-06-14** — The PR-list table is driven by two parallel constants that MUST stay length-aligned: `COLUMN_KEYS` (header keys + order) and `GRID` (CSS grid-template tracks). Adding a column = add to both AND render a matching cell in `PRRow.tsx`, else header/cells misalign silently. Evidence: `client/src/app/repos/[repoId]/pulls/constants.ts:27,42`.
- **2026-06-14** — i18n has only the `en` locale (`client/messages/en/`); new UI strings need a key under the right namespace file (e.g. `prReview.json`, `runs.json`) read via `useTranslations("<ns>")`. A missing key renders the raw key, not an error. Evidence: `client/messages/en/prReview.json:89`.
- **2026-09-18** — Tailwind v4 is INSTALLED but the components do not use it: `client/postcss.config.mjs` registers `@tailwindcss/postcss`, yet every component styles through a colocated `styles.ts` exporting an `s` object of `CSSProperties`, with colours as CSS custom properties from `vendor/ui/styles.css` (`var(--border)`, `var(--crit)`). Reading package.json and reaching for utility classes writes code in the wrong style for this repo. Related: the App Router is used for routing and layouts only — 54 of 116 .tsx files carry `"use client"`, pages included, and rendering plus data go through TanStack Query against the Fastify API. Evidence: `client/postcss.config.mjs:4`, `client/src/app/repos/[repoId]/pulls/[number]/_components/FindingCard/styles.ts:5`.
- **2026-09-19** — A side drawer on `/skills` is NOT a missing feature — it was built and deliberately removed, so re-adding one silently reverts a documented decision. `SkillsListView.tsx:1-6` records it in its header ("It used to open a side drawer that duplicated that tab and carried an Edit skill button to reach it — two steps and two renderings of the same body, for one destination") and `client/specs/L02-skills.md` R2 states the same as a requirement, with acceptance criterion 3 asserting a card click "opens no drawer". A later course criterion asks for exactly that drawer back (preview in a side panel rather than a page). Whichever way that lands, the spec is the thing to change first: leaving R2 and criterion 3 in place while adding the drawer makes the test suite and the spec argue with the feature, and the next session cannot tell which one is stale. Same trap applies to the two other places L02 chose against the mock on purpose: the Evals tab is absent rather than a placeholder (R3) and `PULL FREQUENCY` is deliberately not built (R11).
- **2026-09-19** — The app shell is PRE-WIRED for screens that do not exist yet: `activeKeyFor` already maps `/conventions`, `/multi-agent`, `/context`, `/eval`, `/memory`, `/ci-runs` and `/agent-performance` to sidebar keys. Adding the Conventions page therefore needed nothing but a `NAV` entry whose `key` is `conventions` — highlighting, the command palette (`useShellCommands` walks `NAV`) and the `g <key>` shortcut (`useGlobalShortcuts` matches `item.gKey`) all came for free. Check that helper before wiring anything shell-related by hand for a new route. A repo-scoped item puts `:repoId` in its href and `resolveHref` fills it, falling back to `_` when no repo is active — which lands on the shared `RepoNotFound` screen rather than an API error. Evidence: `client/src/components/app-shell/helpers.ts:26`, `client/src/vendor/ui/nav.ts:40`, `client/src/components/app-shell/hooks/useGlobalShortcuts.ts:45`.

## Tool & Library Notes

- **2026-09-16** — A bare `toLocaleString()` formats with the MACHINE locale, not the app's: the same token total rendered "9 119" in the browser (uk-locale OS, narrow no-break space) and "9,119" under vitest/jsdom, so a test asserting that string passes locally and breaks elsewhere. The UI ships only the `en` locale — pass it explicitly: `total.toLocaleString("en-US")`. Evidence: `client/src/components/RunCostBadge/RunCostBadge.tsx:41`.
- **2026-09-18** — Do NOT run `pnpm build` in `client/` while `pnpm dev` is serving: both write the same `.next` directory, and the build leaves the running dev server handing out chunk hashes that no longer exist. The symptom is not a module error but `Uncaught TypeError: Cannot read properties of undefined (reading "call")` from `next-server/app-page.runtime.dev.js` plus a run of 404s on `/_next/static/chunks/*`, while `curl localhost:3000` still returns 200 HTML and the page renders its static shell with every data-driven section missing. It reads exactly like a broken React tree, so it costs a real debugging detour. Recovery is to stop the dev server and start it again (`.next` is gitignored; deleting it usually fails on Windows while the server holds the file locks). To verify a build-level change without touching a live dev server, build once and restart dev afterwards, or build in a throwaway copy.

## Recurring Errors & Fixes

- **2026-09-16** — Em-dash "—" is the app-wide empty marker, so adding any new empty-capable cell to a row breaks EXISTING sibling tests that assert `getByText("—")` — RTL throws "found multiple elements", not a soft failure. Adding the FINDINGS cell broke two passing COST tests in `PRRow.test.tsx` this way. Fix: give the shared `pr()` fixture a non-empty default for the new field so only one cell is empty per test, and override it explicitly in the cases that test emptiness. Evidence: `client/src/app/repos/[repoId]/pulls/_components/PRRow/PRRow.test.tsx:38`.
- **2026-09-18** — RTL's `getByDisplayValue` NORMALISES whitespace before matching, so it can never find a multi-line `<textarea>` value: `getByDisplayValue(skill.body)` on a markdown body containing a blank line fails with "Unable to find an element with the display value: # Rubric" even though the textarea holds exactly that string. The symptom points at the component, not at the query. Fix used in `skills/[id]/_components/SkillEditor/SkillEditor.test.tsx:53`: query by role and pick the element — `screen.getAllByRole("textbox").find((el) => el.tagName === "TEXTAREA")` — then assert with `toHaveValue(body)`, which does not normalise. Single-line inputs are unaffected. Related: this repo has NO `@testing-library/user-event`; interactions go through `fireEvent` (`fireEvent.change(el, { target: { value } })`), matching `FindingCard.test.tsx` / `FindingsPanel.test.tsx`.
- **2026-09-19** — Opening a modal from a button that shares its label duplicates an accessible name, and `getByRole("button", { name })` then throws "found multiple elements" — the toolbar `Create skill` opens a modal whose footer button is also `Create skill`. A regex anchor does not help, because both names match exactly. `Modal` sets `role="dialog"` (`client/src/vendor/ui/kit/Modal.tsx:26`), so the fix is to scope the query: `const dialog = within(screen.getByRole("dialog")); dialog.getByRole("button", { name: "Create skill" })`. Same family as the em-dash "found multiple elements" trap, but triggered by a LABEL collision rather than by an empty cell. Evidence: `client/src/app/repos/[repoId]/conventions/_components/ConventionsView/ConventionsView.test.tsx:215`.
